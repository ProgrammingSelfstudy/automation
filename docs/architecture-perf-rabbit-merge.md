# 技术方案：性能测试模块（perf-rabbit）并入 automation 平台

## 背景

`automation`（原"接口压测平台"）目前只有一个模块：接口压测（多用户 Web 应用，Go 标准库 `net/http` + MySQL + Session/TOTP 鉴权，WebSocket 推送任务进度）。团队另有一个独立在跑的本地工具 `perf_rabbit`（Go + Gin，控制 `adb`/`pymobiledevice3` 采集手机 CPU/内存/FPS/卡顿等性能指标，文件存储，内嵌自己的 React 前端，无鉴权，单用户本地使用），以及它的一个独立前端 `perf_rabbit_web`。

本文档给出把 perf-rabbit 并入 automation、成为其"性能测试"模块的技术方案：设计原则、方案对比、为什么选这个方案、好处、弊端、以及一段主动质疑自己结论的反向思考。

## 现状对比

| | 接口压测（现有） | perf-rabbit（待并入） |
|---|---|---|
| 后端框架 | 标准库 `net/http`（Go 1.22+ 路由） | Gin |
| 鉴权 | Session Cookie + TOTP 2FA，多用户 | 无，单用户本地工具 |
| 数据存储 | MySQL（每个 `xxxstore` 包一张表） | 本地文件（`data/perf/<taskId>.json` + `.csv`） |
| 实时通信 | WebSocket（`internal/logevent` 广播任务进度） | HTTP 轮询（前端每秒 `GET /api/collect/perf/:taskId?from=N`） |
| 部署形态 | 服务器长期运行的服务（systemd 管理） | 用户本地运行的可执行文件（`cmd/app` 内嵌前端，双击即用） |
| 前端 | 一个 React 应用，多模块导航 | 独立 React 应用，内嵌进 Go 二进制 |
| 核心能力依赖 | 只需要网络能访问被测 API | 必须能通过 USB/局域网访问物理设备（`adb`/`pymobiledevice3`） |

最后一行是这次方案设计里绕不开的硬约束，下面第一个原则就是从它推出来的。

## 设计原则

选型不是拍脑袋，每一条都对应下面方案设计里的一个具体决定：

1. **物理约束不可协商，架构必须显式承认它**——`adb`/`pymobiledevice3` 只能在设备实际接入的机器上执行，这是物理事实，不是可以靠软件设计绕开的技术问题。好的架构不是假装约束不存在，而是把约束画进架构图里，让每个后来看这份文档的人一眼看出"为什么要有本地 Agent 这层"。
2. **关注点分离（Separation of Concerns）**——"设备 I/O"和"数据的持久化/多端可见"是两个完全不同的关注点，前者天然是本地的、有状态的、跟硬件强绑定；后者天然是中心化的、无状态的、可以随便换机器看。把它们分别放进"本地 Agent"和"中心平台"两个进程里，而不是想办法揉进一个进程，是这条原则的直接应用。
3. **接口的形状要匹配它描述的行为（对接口做单一职责校验）**——`task.Module` 接口的方法签名（`Run(ctx, task, accounts) (RunResult, error)`）描述的是"一次性、批量、同步返回结果"的行为。性能采集是"长会话、持续推送、用户随时中断"的行为。两种行为形状不同，就不该共用同一个接口，这不是感觉上"更规范"，是接口契约本身的要求——一个接口如果要同时表达两种不兼容的行为，它的调用方永远得写一堆 `if` 分支去猜"这次到底是哪种情况"，这正是接口设计要避免的坏味道。
4. **高内聚低耦合，但"合并"要合的是用户体验，不是实现细节**——用户要的"合并成一个东西"，本质是"一次登录、一个界面、看起来是同一个产品"，这是体验层面的耦合，应该做紧。而"Gin 还是标准库""文件还是 MySQL"这些是实现细节层面的耦合，不该为了"看起来更合并"而强行拉平——两个模块的实现细节保持独立，用户感知不到，也不该感知到。
5. **可逆的决定优先于不可逆的决定（Reversible-first）**——Phase 1 保留 perf-rabbit 独立的 `go.mod`，不是偷懒，是因为"两个 module 何时合并成一个"是一个几乎零成本可以往后拖、拖到 Phase 2 真正需要时再做的决定；反过来如果 Phase 1 就把两套依赖强行拉进一个 `go.mod`，一旦发现版本冲突或者想反悔，成本高得多。优先做便宜的、可逆的决定，把贵的、难逆转的决定往后放到信息更充分的时候再做。
6. **YAGNI（You Aren't Gonna Need It）**——这版没有引入缓存层、没有设计多租户权限模型、没有做 Agent 版本兼容矩阵，是因为现在没有证据表明需要这些东西。真的需要的时候再加，好过现在就为"可能用得上"的场景预先设计一套用不上的复杂度。
7. **这套模式要为以后陆续加模块复用，不是给 perf-rabbit 开的一次性特例**——automation 以后会持续加新模块，不会只有"接口压测 + 性能测试"这两个。这次定的套路（同一次登录/同一套 UI 外壳作为不可谈判的统一层；每个模块的技术栈、存储方式按自己的场景选，不强求所有模块用同一套 Go 依赖或者同一种数据模型）应该成为以后每加一个新模块时默认参照的模板，而不是每次都重新讨论一遍"要不要合并、怎么合并"。以后新模块接入时，直接对照这份文档的判断标准（用户体验层面必须统一、实现细节层面允许独立）即可，不用每次从零推导。

## 方案对比矩阵

除了下面详细展开的"中心平台 + 本地 Agent"，认真考虑过另外两个方案，逐条打分（1-5，5 最好）：

| 评估维度 | 方案 1：两套完全独立部署 | 方案 2：强套 `task.Module`，单进程跑 | 方案 3（选定）：中心平台 + 本地 Agent |
|---|---|---|---|
| 是否满足"合并成一个"的用户要求 | 1（完全没合并） | 5（字面意义上合并） | 4（体验上合并，进程上没有——见下面反向思考） |
| 实现成本 | 5（不用改代码） | 2（要么削足适履改 `task.Module` 语义，要么破坏接口设计原则） | 3（要新增 WS 通道、上报接口、探测逻辑） |
| 物理约束处理是否诚实 | 3（回避了问题，只是没合并所以不冲突） | 1（假装单进程能解决物理无法解决的问题，实际部署到服务器后功能会直接不可用） | 5（约束被显式设计进架构） |
| 未来可维护性 | 2（两套东西永远长成两个样子） | 2（接口语义污染，其它模块看这个接口会更难理解 `Module` 到底该是什么形状） | 4 |
| 用户体验一致性 | 1（两个入口两套登录） | 5（如果真能跑起来） | 4（一个入口一套登录，但需要多一步"下载 Agent"） |

方案 2 在"是否满足用户要求"和"体验一致性"上打分最高，但被否决——因为它的"满足"是假的：把 perf-rabbit 塞进 `task.Module` 之后，部署到服务器上的那个进程依然连不上任何手机，功能照样不可用，只是把"连不上"这个错误从"架构层面提前暴露"变成了"运行时才发现"，对用户是更差的体验，不是更好的。方案 3 是诚实地把"必须本地跑"这件事变成用户能理解、能操作的一个步骤（下载 Agent），而不是假装它不存在。

## 核心约束：物理设备访问

`adb`/`pymobiledevice3` 控制的是"当前这台机器物理连接（或同网段）的手机"，这个能力**只能在设备实际接入的那台机器上执行**。automation 后端部署在 CentOS 服务器上，服务器没有、也不可能有用户测试用的手机接进来——这意味着"性能采集"这个动作本身，无论上层架构怎么设计，物理上都不可能在服务器进程里完成。

这不是这次设计要回避或者绕过的东西，而是要显式地设计进架构里（对应设计原则 1）。

## 设计：中心平台 + 本地 Agent

采集动作放在用户本地执行，其余一切（登录、历史记录存储与查看、跨设备/跨用户可见性）放在中心平台，两者通过 WebSocket + 一次性上报接口连接：

```
┌─────────────────────────────┐         ┌──────────────────────────────┐
│  automation 中心平台（服务器）  │         │  本地 Agent（用户电脑，含手机）  │
│                               │         │                                │
│  - 登录/鉴权（沿用现有 session） │         │  - adb / pymobiledevice3 采集   │
│  - 性能测试模块 Web UI          │◄──WS───┤    （perf-rabbit 现有逻辑，       │
│  - MySQL 存历史记录             │  实时   │     已审查修复 3 个 bug）        │
│  - Agent 安装包下载入口         │  推送   │  - 本地 HTTP/WS 服务（复用 :9527）│
│                               │         │                                │
│  POST /api/perf/history  ◄────┼─任务结束时上报最终记录────────────────────┤
└─────────────────────────────┘         └──────────────────────────────┘
```

**中心平台职责**：
- 提供"性能测试"模块入口（左侧导航新增一项，跟"接口测试"平级）
- 提供 Agent 安装包下载（`perf-rabbit/client/release/` 下已经在编译 macOS/Windows 版本，中心平台负责托管这些文件供下载）
- 页面加载时探测本地 Agent 是否在跑（例如打一次 `ws://127.0.0.1:9527/api/ping` 或复用设备列表接口）；探测不到就展示"请先下载并启动本地采集工具"的引导提示 + 下载按钮，**不报错崩页面**
- 探测到 Agent 后，浏览器直接跟本地 Agent 建立 WebSocket 连接做实时交互（选设备、选 App、开始/停止采集、实时接收样本），这条连接完全在用户本机内网/回环地址上，不经过中心平台服务器转发
- 采集任务停止后，把完整记录（对应现有 `PerfHistoryRecord` 结构）存进 MySQL——这一步可以是本地 Agent 直接 `POST` 给中心平台的登录用户身份下（需要 Agent 拿到当前登录用户的一个短期上报凭证，或者更简单：由浏览器在收到 Agent 通过 WS 推送的"任务已停止，最终记录如下"消息后，由浏览器自己带着已有的 session cookie 转发 `POST` 给中心平台——这样不需要给本地 Agent 单独设计一套认证机制，复用浏览器已有的登录态，是 Phase 2 要在两种方案里选一个的点，目前倾向后者，因为不用给 Agent 端另外做鉴权）
- 历史记录查询/详情/导出/删除，全部走中心平台的 MySQL，不再依赖"当时采集用的那台电脑还留着那个文件"

**本地 Agent 职责**：
- 保留 perf-rabbit 现有的设备发现、采集调度、iOS/Android 指标采集逻辑（`internal/perf`、`internal/device_list`、`internal/get_device_apps` 这些包，这次审查已经修过 3 个真实 bug：`ios_graphics.go` stderr 误当数据解析、`stop_collect.go` 重复保存覆盖 `stop_time`、`python.go` 版本校验用错路径，都是可以直接复用的代码基础）
- 本地起一个 HTTP/WS 服务（沿用现有 `:9527`，`PERF_RABBIT_DEV_PORT` 可覆盖）
- 采集到新样本后通过 WebSocket 主动推送给已连接的浏览器，替换掉现在"浏览器每秒主动来问一次"的轮询模式——一是省掉 1 秒延迟和空轮询的开销，二是跟接口压测那边任务进度推送保持同一套通信范式，不用前端同时维护"WS 一套、轮询另一套"两种数据流处理逻辑
- 任务停止后，把完整记录通过已经建立的 WS 连接（或者一次性 HTTP 回调）交给浏览器，由浏览器负责最终把这条记录持久化到中心平台

## 为什么不字面套用 `internal/task.Module` 接口

现有 `task.Module` 接口：

```go
type Module interface {
    Type() string
    ValidateConfig(cfg json.RawMessage) error
    ExecutionCount(cfg json.RawMessage) (int, error)
    Run(ctx context.Context, t *Task, accounts []*accountpool.Account) (RunResult, error)
}
```

这是为"账号池 + 一次性批量跑 N 次 + 拿结果"这种压测场景设计的：一次 `Run` 调用有明确的开始和结束，中途不需要外部交互。性能采集是完全不同的交互形状：用户选一台设备一个 App、点开始、这个会话可能持续几分钟到几十分钟、期间要不断把新数据推给正在看着的用户、用户随时可能点停止。硬把这种长会话塞进一次同步的 `Run(ctx, task, accounts)` 调用里，接口签名对不上、语义也对不上，除了"看起来都叫 Module"没有任何实际好处（对应设计原则 3）。

"合并成一个 Module"这个目标，落地方式是：**同一个 Go 进程、同一个 Web 前端外壳、复用同一套登录鉴权**，但性能测试模块内部走自己独立的一组路由（`/api/perf/...`）和自己的任务管理逻辑（沿用 perf-rabbit 现有的 `Manager`），不通过 `task.Module` 这个接口。这是技术判断，不是对"合并"这个要求打折扣。

## 数据存储：MySQL 表结构草案

替换掉 `data/perf/<taskId>.json`/`.csv` 文件存储，新增 `internal/perfstore` 包（跟现有 `environmentstore`/`interfacestore` 同一套模式）。两种表结构留到 Phase 2 实现时最终确定，这里给出取舍：

**方案 A：一张表，samples 整体存一个 JSON 列**（仿照 `environmentstore.variables`/`scenariostore.definition` 已经在用的模式）
```sql
CREATE TABLE perf_task (
    id               BIGINT AUTO_INCREMENT PRIMARY KEY,  -- 短数字 ID，压测时口头对答案/贴日志方便，产品决定不用 UUID
    user_id          VARCHAR(36) NOT NULL,   -- 上报这条记录的登录用户，仅做归属记录，不做可见性过滤（见下面"好处"里的说明）
    device_id        VARCHAR(128) NOT NULL,
    package_name     VARCHAR(255) NOT NULL,
    process_name     VARCHAR(255) NOT NULL,
    platform         VARCHAR(16) NOT NULL,
    device_model     VARCHAR(64),
    status           VARCHAR(16) NOT NULL,   -- stopped / interrupted
    start_time       DATETIME NOT NULL,
    stop_time        DATETIME NOT NULL,
    sample_interval_ms BIGINT NOT NULL,
    sample_count     INT NOT NULL,
    last_error       TEXT,
    samples          JSON NOT NULL,          -- 完整时间序列，一次性存
    created_at       DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    INDEX idx_user (user_id)
);
```
- 好处：实现简单，跟现有代码风格一致，一次查询拿到完整记录
- 代价：单条记录可能几十上百 KB（几十分钟的采集，每秒一条样本），历史列表页如果不小心 `SELECT *` 会很重（要像现在 `PerfHistorySummary` 那样，列表接口单独 `SELECT` 不含 `samples` 的字段）；采集时间如果拉到几个小时，单条记录会更大，虽然远没到 MySQL 单行/单列的物理上限，但值得在 Phase 2 定个"单次采集时长上限"的产品规则

**方案 B：拆两张表**，`perf_task`（元信息）+ `perf_sample`（每条样本一行，`task_id` 外键）
- 好处：可以对样本做时间范围查询/聚合，历史列表天然不会带上大字段
- 代价：多引入一张表、多一次 JOIN，写入是"一次采集一条 INSERT"而不是"停止时一次性写入"，实现复杂度明显更高

**倾向 A**：性能采集的查询场景基本是"要么看列表摘要，要么看某一条的完整时序图表"，不需要跨任务对单条样本做 SQL 层面的过滤/聚合，方案 B 的额外能力用不上，方案 A 更简单、跟现有代码库风格更统一（对应设计原则 6，YAGNI）。最终由 Phase 2 实现时确认。

**这版没有引入任何缓存层**（Redis、内存缓存等）——MySQL 直接读写、WebSocket 直接推送，不需要。以后如果因为并发量或者查询性能问题需要加缓存，会先跟你说清楚要加什么、加在哪一层，再动手，不会不声不响加进去。

## 好处

- **统一入口**：一次登录，接口压测和性能测试共用同一个 Web 界面、同一套账号体系
- **历史记录多端可见**：现在 perf-rabbit 的采集记录锁在"当时那台电脑的本地文件"里，换台电脑就看不到；并入之后存 MySQL，谁登录都能看团队里任何一次采集的历史（产品已确认：数据展示不做隔离，所有登录用户可见全部记录，`user_id` 只留归属信息，不加可见性过滤）
- **代码可发现性**：以后新人加入，一个仓库能看到公司内部全部自研工具，不用到处打听"性能采集那个工具的仓库在哪"
- **为真正的数据打通留了口子**：以后如果想做"这次接口压测跑的时候顺便看一眼手机端的性能曲线"，两边数据都在同一个 MySQL 里，做关联查询/统一报表是自然而然的事；如果两边一直是完全独立的两个系统，这种关联能力以后要专门补一套同步机制
- **通信范式统一**：性能采集也走 WebSocket 推送之后，前端只需要维护一套"处理服务端推送"的逻辑，不用一边处理 WS 消息一边处理轮询结果

## 弊端（如实列出，不回避）

- **多了一个"需要下载安装本地程序"的环节**：纯 Web 应用做不到访问 USB 设备，这是没有办法绕开的代价，用户体验上比"打开网页就能用"重
- **下载 Agent 不等于马上能用，用户电脑还要装好底层环境**：Android 采集需要用户电脑上单独装好 `adb`（Android SDK platform-tools）并配进 PATH，Agent 自己不会装；iOS 采集需要 Python 3.8+，`pymobiledevice3` 这个包 Agent 会自动装，但 Python 本身没装的话不会帮用户装。也就是说"下载 -> 双击打开 -> 能用"这个理想流程只对已经装过这些环境的开发者成立，第一次用的人大概率还要先跟着一份环境配置说明走一遍，这个门槛需要在下载入口页面写清楚，不能假设用户电脑上已经有
- **本地 Agent 版本和中心平台 API 版本可能不同步**：用户电脑上装的 Agent 版本落后于中心平台，接口字段对不上——需要设计版本兼容检查（Agent 启动时上报自己版本号，中心平台判断是否需要提示升级），这次方案不含具体实现，先记录为已知限制
- **Phase 1 阶段两套独立 go.mod/npm 项目共存**：`perf-rabbit/client` 用 Gin，短期内 CI 要拆两套 Go 流水线、两套前端流水线跑，维护成本没有因为"放进同一个仓库"而立刻降低，等 Phase 2 把 Gin 改写成标准库、合并进主 go.mod 之后才会真正统一
- **Agent 上报中心平台如果网络中断，目前没有重试/离线暂存设计**：本地采集完成、正准备上报时如果断网，或者用户在上报之前就直接关掉了浏览器标签页，这条记录目前会怎么处理（本地兜底存一份？丢弃？提示用户手动重传？）需要专门设计，这次方案不含，记录为已知限制——这是当前方案里最薄弱的一环，见下面反向思考
- **多用户数据隔离目前只是表结构里预留了 `user_id` 列，没有具体的权限模型**：是不是所有登录用户都能看所有人的性能记录，还是要分团队/分项目隔离，这个产品层面的问题需要你来定，会影响 Phase 4 的具体实现

## 反向思考：主动挑战上面的结论

架构决策不应该只列一堆支持自己的理由。下面是几个认真考虑过、可能推翻或者削弱上述方案的角度：

**1. "浏览器转发上报"这个设计有单点丢失数据的风险，比文档前面轻描淡写的更严重。**
最终记录要不要真的存进 MySQL，依赖用户没有在"采集停止"和"浏览器收到并转发完"这个窗口期之间关掉标签页、断网、电脑睡眠。如果这个窗口期哪怕几秒钟都不能容忍数据丢失，那么"本地 Agent 直接上报"（不经过浏览器转发）其实是更稳的方案，代价是要单独给 Agent 设计一套认证（比如让用户在 Agent 里粘贴一个从网页复制出来的长期 token）。**如果这个模块以后被当作正式的性能基线工具、每次采集的数据都很宝贵，不能接受偶尔丢失**，现在这版"浏览器兜底转发"的设计需要重新评估，应该优先做"Agent 直接上报 + 本地失败重试队列"。

**2. WebSocket 不是免费的，轮询在这个场景下可能被低估了。**
文档把"WebSocket 替代轮询"列进了好处，但要诚实地说：轮询是无状态的，断了下一次请求重新来就行，实现和排错都简单；WebSocket 要处理连接保活、断线重连、消息丢失后怎么补数据这几件轮询不用管的事。性能采集是"每秒一条数据"的低频场景，轮询的额外开销本来就不大。这次选 WebSocket 主要是为了"跟接口压测那边的通信范式统一"这个工程一致性的理由，**不是因为轮询在这个具体场景下真的不能用**。如果 Phase 2 实现 WebSocket 版本时发现断线重连、消息补发这些边界情况处理起来比预想的复杂，退回轮询（哪怕只是先用轮询把 Phase 2 其它部分跑通，WebSocket 单独作为 Phase 2.5 再做）是完全合理的选择，不是失败。

**3. 本地 Agent 这层复杂度，在特定部署场景下可能是不必要的。**
现在的前提是"服务器在公网、用户电脑和服务器不在同一网络"，这种情况下服务器物理上够不到用户的手机，所以需要本地 Agent 搭桥。但如果 automation 以后改成部署在**公司内网**（而不是现在这台腾讯云 CentOS 服务器），并且测试用的手机也在同一个内网段，那么用 Android 的无线调试（`adb connect <手机内网IP>:5555`）直接从服务器连手机，理论上是可行的，根本不需要用户下载安装本地 Agent。**这个方案没有被选中，不是因为它不好，是因为它只在"服务器和设备同一局域网"这个特定场景下成立，当前腾讯云公网部署的场景不满足这个前提**。如果部署环境变了（比如以后真的上了内网），这一整套 Agent 架构的必要性需要重新评估，不应该不假思索地延续。

**结论**：中心平台 + 本地 Agent 这个方案，是在"服务器和设备不在同一网络、数据丢失可以接受偶发概率、团队愿意接受 WebSocket 的实现复杂度"这三个前提下成立的。三个前提任何一个变了，都值得回来重新看这份文档，而不是机械地按 Phase 2/3/4 往下推。
